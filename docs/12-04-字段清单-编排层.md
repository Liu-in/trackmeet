# 编排层字段清单

> 本文件列出编排层 8 张表的**业务字段**。通用字段见 [字段清单总览](12-00-字段清单总览.md)（`id, meet_id, create_by, create_time, update_by, update_time, deleted, version`），此处不再重复。
> 类型遵循总览第 1 节类型规范；枚举取值遵循总览第 4 节约定；命名与约束遵循总览第 3 节规范。
> 对应需求：FR-SCH-01 ~ FR-SCH-13；性能目标见 NFR-02（单届 5000 人 / 300 项目 / 200 分组下自动编排 ≤ 10s、列表查询 ≤ 1s）。

### schedule_session 竞赛单元表
> 一个竞赛单元 = 某半天（上午/下午/晚上）在一个场地上的比赛时段，是日程条目的时间容器

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `session_name` | VARCHAR(100) | 单元名称，如「第一天上午」 |
| `session_date` | DATE | 单元日期 |
| `day_no` | SMALLINT | 赛期第几天，从 1 开始 |
| `period` | VARCHAR(32) | 时段，MORNING/AFTERNOON/EVENING |
| `start_time` | TIME | 单元开始时刻 |
| `end_time` | TIME | 单元结束时刻 |
| `venue_id` | BIGINT UNSIGNED | 主场地 `venue.id` |
| `venue_ids_json` | JSON | 同时可用场地 ID 列表 |
| `total_minutes` | SMALLINT | 单元可用总时长（分钟） |
| `used_minutes` | SMALLINT | 已排入时长（分钟），编排后回填 |
| `item_count` | SMALLINT | 单元内日程条目数 |
| `is_locked` | TINYINT(1) | 单元是否锁定，锁定后不接受自动排入 |
| `locked_by` | BIGINT UNSIGNED | 锁定人 `sys_user.id` |
| `lock_time` | DATETIME | 锁定时间 |
| `publish_status` | VARCHAR(32) | DRAFT 草稿 / PUBLISHED 已发布 |

**索引与约束**：`uk(meet_id, session_date, period)`、`idx(meet_id, session_date, sort_no)`、`idx(venue_id, session_date)`

## 编排链路说明

- `schedule_session`（竞赛单元：日期 / 半天 / 场地 / 起止时间）
  - `schedule`（日程条目：`event_round` × `venue` × 时间窗 × 组数 × 时长，挂 `session_id`）
    - `heat`（分组：`schedule_id` + `heat_no`，含道数、检录时间、状态）
      - `heat_member`（组内人员：`heat_id` + `registration_id` + `athlete_id` + `unit_id` + `bib_no` + `order_no`）
        - `lane`（径赛道次：`heat_member_id` ↔ `lane_no`，一对一）
        - `field_order`（田赛顺序：`heat_member_id` ↔ `order_no`，一对一）
- 写入顺序（一次自动编排事务内）：先建/复用 `schedule_session` → 写 `schedule`（分配单元、场地、时间窗、`order_no`、`batch_no`）→ 按 `heat_count` 写 `heat` → 按分组算法写 `heat_member`（含 `order_no`、`is_seed`）→ 径赛写 `lane`、田赛写 `field_order` → 回填 `heat.member_count`、`schedule.member_count`、`schedule_session.used_minutes/item_count` → 执行冲突检测写 `conflict_log` → 回填 `schedule.conflict_flag/conflict_count` → 生成 `schedule_snapshot`。
- 回滚顺序：取 `schedule_snapshot.snapshot_json` → 将当前结果另存为新快照（`snapshot_type=RESTORE`）→ 清理非锁定的 `lane`/`field_order`/`heat_member`/`heat` 后按快照重建 → 切换 `is_current`。

## 本层设计要点

1. **三级锁定与重排**：`is_locked`/`locked_by`/`lock_time` 在 `schedule`、`heat`、`lane`、`field_order` 四级同构。重排时先取全部锁定项作为固定约束，父级锁定则其子级整体冻结；仅对未锁定项重新计算 `session_id`、`order_no`、`lane_no`。
2. **冲突检测的数据基础**：检测依赖 `schedule(plan_start_time, plan_end_time, venue_id)` + `heat_member(athlete_id/registration_id)` + `referee_assignment`；间隔类冲突用 `interval_minutes` 与规则阈值 `required_interval_min` 比较，结果全部落 `conflict_log.detail_json` 以支持可视化定位（FR-SCH-07）。
3. **拖拽调整落库**：拖拽日程只更新 `schedule.session_id`、`order_no`、`plan_start_time/plan_end_time`，累加 `move_count` 并写 `adjust_reason`、`source_type=MANUAL`；组内调序改 `heat_member.order_no`/`field_order.order_no`；换道写 `lane.lane_no` 并留 `swap_group/swap_from_lane/swap_reason/swap_by/swap_time`，同时写 `sys_operation_log`。
4. **并发乐观锁**：`schedule`、`heat`、`schedule_session` 使用通用 `version` 列，编排员与裁判同时改动时校验版本，冲突返回 `409`；道次/顺序类单行调整以 `heat_member_id` 与 `uk(heat_id, lane_no)`、`uk(heat_id, order_no)` 兜底唯一性。
5. **快照与回滚**：每次自动编排、批量手工调整前后生成 `schedule_snapshot`，`snapshot_json` 承载完整链路数据，`is_current` 标记生效版本，`batch_no` 串联同一批次的日程、分组、道次与冲突记录，实现「按批次回退」。
6. **发布与可见性**：`schedule`/`schedule_session` 的 `publish_status`、`publish_time`、`publisher_id` 控制秩序册对领队与观众可见（FR-SCH-13）；发布后仍在草稿态的项目不进入对外查询，草稿态允许继续重排。
7. **检录与成绩衔接**：`heat_member` 冗余 `registration_id`、`athlete_id`、`unit_id`、`bib_no`、`group_id`，检录表与成绩录入可直接按 `heat_member_id` 定位，避免多表回溯；`is_scratch`/`status` 支持 DNS 前状态与后续 `result.status` 对齐。
8. **性能索引**：面向 NFR-02，主查询路径 `idx(meet_id, session_id, order_no)`（日程表渲染）、`idx(venue_id, plan_start_time)`（场地冲突检测）、`idx(meet_id, schedule_id, registration_id)`（人员定位）、`idx(meet_id, conflict_type, resolved)`（冲突清单）均为等值列在前、范围列在后；`snapshot_json`、`detail_json`、`lane_order_json` 只作留痕，不参与高频过滤。
